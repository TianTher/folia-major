# 多 P 视频：拆成独立歌曲、合并展示、按 P 切换（TODO，暂不实现）

bilibili 的一个 `bvid` 可以有多 P（分 P）：一个合集视频下，每一 P 有自己的 `cid`、标题、时长。现在整个
`bvid` 是**一首歌**，播的是第一 P 的音轨（收藏夹列表给的 `ugc.first_cid`）。这份文档是把每一 P 做成独立歌曲、
界面上仍按"一个视频"合并展示的设计与实施顺序。

## 1. 已经就绪的部分（2026-11-26 已实现）

- `idsOf` 认得 `bvid:p<n>` 这种 id：解析出 `bvid` 与 `n`，`view` 取 `pages[n-1].cid`，越界回退第一 P
  （`sources/bilibili/core/bilibiliCapabilities.ts`）。
- 普通 `bvid`（整条视频）不再白跑 `view`：收藏夹列表给的 `first_cid` 就是第一 P 的 cid。
- `data.pages` 是**分 P 数**（`resource/list` 的 `page` 字段，实测 2026-11-24 记在
  `docs/bilibili-source-plan.md` §"收藏夹条目"）。

## 2. 歌曲模型

| 字段 | 整条视频（今天） | 分 P（目标） |
| --- | --- | --- |
| `id` | `BV1xx…` | `BV1xx…:p2` |
| 标题 | 视频标题 | 视频标题 · P 标题（P1 与整条视频同标题） |
| `durationMs` | 视频时长 | 该 P 的时长（`view.pages[n-1].duration`，秒） |
| `data.cid` | `ugc.first_cid` | 该 P 的 cid |
| `data.avid` / `data.bvid` | avid | avid |
| `data.part` | 无 | `n`（1 起） |
| `data.parts` | `page`（分 P 数） | 分 P 数（同一视频的每一 P 都带） |
| `data.groupId` | 无 | `bvid`，供界面按组展示 |

歌词：`playerInfo(aid, cid)` 本来就按 cid 取，分 P 各自一份，无需额外改动。

## 3. 列表模型（界面合并展示）

宿主现在的歌单页是**平铺列表**：`catalog.getPlaylistTracks` 交一串歌，宿主一条一行画出来。要让"一个视频"占一行、
展开才看到各 P，需要宿主侧多一个概念，不能只靠音源。

两种做法，取决于以后愿不愿意再动宿主契约：

**A. 音源交分组（推荐）**
给 `catalog@1` 加一个可选的"这一页里有分组"的回报，例如每首歌带 `group?: { id, title, coverUrl, total }`，
并让宿主在渲染时把相邻、同 `group` 的条目收成一行（默认折叠）。
- 改动：`src/mods/folium/sources/contract.ts`（`FoliumSourceSong.group`）、adapter、歌单页列表组件；
- 好处：一次改动同时服务所有平台（B 站以外也能用），音源侧只是"给数据加字段"。

**B. 音源自己交一整组**
`getPlaylistTracks` 仍然交平铺的歌，但另给一个 `getPlaylistGroups` 之类的能力，宿主拿分组结构自己画。
- 好处：宿主列表模型不变；
- 代价：等于在契约里开第二个"列表"入口，两套数据要对得上，容易不一致。

## 4. 展开与分页（用户描述的交互）

- 歌单页 / 收藏夹歌曲选择页：多 P 视频那一行右侧一个展开按钮（lucide `chevron-down`）；
- 展开后：该视频的 P 列表，**两列**并排，**每页 10 个**（5 行 × 2 列），超过 10 个给上一页 / 下一页；
- 展开状态不持久化（离开页面即收起），展开的那一组在滚动回顶部时保持。

宿主侧的落点：歌单页列表组件（`src/components/app/home/` 一带）与收藏夹页（同一套列表渲染）各加一个可折叠行，
分页只要本地状态 `page`，不需要新请求（P 列表随第一页数据一起下来）。**一页 10 个**是纯前端分页。

## 5. 播放与"下一曲"

需求：同一视频内，下一曲 = 下一 P；到最后一 P 才进入下一个视频。上一曲同理。

实现要点：
1. 队列里放的是**每一 P 各自一条**（`bvid:p<n>`），按 P 顺序压入，所以宿主的"下一曲"天然就是下一 P；
2. 换到下一个视频要在**最后一个 P 之后**：入队时按"视频 → 它的所有 P"顺序展开，宿主的顺序播放就对；
3. 单曲循环 / 随机播放按宿主现有语义走（随机时 P 会被打散，这是可接受的）；
4. "播整条视频"（不展开时）：点一行播第一 P，此时队列里应有该视频后续所有 P——即"点一行 = 把这个视频的 P 全压进队列并播第一个"。

## 6. 待定的取舍

1. **默认拆不拆**：每次都展开成 P（歌单一屏变长很多）还是只在用户点开时才展开、点整条视频时按"整条播到底"入队？
   我倾向：列表里默认折叠，**点整条视频入队的是它的全部 P**，点某一 P 入队的是"该 P 起，到该视频最后一 P 为止"。
2. **搜索/推荐里的多 P**：搜索结果按"整条视频"给（与今天一致），否则同一个视频会占满一页。
3. **时长/封面**：P 级封面 bilibili 不提供（`view.pages[n]` 没有 pic），P 沿用视频封面。
4. **分 P 数的上限**：实测见过 100+ P 的合集，前端一页 10 个的分页够用；但音乐播放器里 100 P 的合集大多不是歌，
   要不要按"P 数 > N 不拆"设个阈值？待确认。
5. **与收藏夹筛选的关系**：一个视频在筛选里是"一个收藏夹条目"，拆 P 不影响筛选。

## 7. 实施顺序（建议）

1. **音源侧（可独立验收）**：`getSong('bvid:p2')` 返回分 P 的歌（标题、时长、cid、part/parts/groupId），
   `getPlaylistTracks` 仍是整条视频（界面不变）；用 `getSong` + 单测验证 P 的 cid/时长对得上。
2. **播放验证**：手动把 `bvid:p2` 塞进队列，确认播的是 P2 的音轨、歌词也是 P2 的。
3. **宿主契约**：选 A 或 B（§3），加 `group` 字段与其渲染；先只做歌单页。
4. **展开 UI**：折叠行 + 两列 + 每页 10 个 + 翻页。
5. **入队语义**：点整条 / 点某一 P 两种入队（§5.4、§6.1）。
6. **回归**：单 P 视频行为与今天完全一致（所有新字段缺省时不分组）。

## 8. 不在这次范围内

- 视频章节（`view.pages` 之外的 `chapter`）不做；
- 合集（`ugc_season`）不拆；
- 分 P 的封面、字幕的语言选择（仍取第一份中文 CC，`ai-*` 排除）。
